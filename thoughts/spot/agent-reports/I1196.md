# I1196: catalogue song count blocks the library worker

## Problem

`sel_library_song_total` (db.c:696, op `SEL_USER_LIBRARY_COUNT` in folders.c) ran `SELECT COUNT(*) FROM songs` on the
single library worker. On a cold 645 000-song library the count walks every page of the songs key index. Every
interactive read the engine posts (sidebar, pages) queues behind it on the same worker, so a sidebar click in the
first seconds got hit=0 about one run in three, and `sel_engine_destroy` spun in `lib_read_end(&e->rd_total)` until
the count finished (about 10 s at quit, I1195).

Violated invariant: a slow aggregate read must never block interactive reads or engine shutdown. Root-cause level:
the query itself (library db layer), not the engine's read scheduling.

## Measurements (copy of the real library.db in the session scratchpad, cold cache via `ditto --nocache`)

| Query | Cold | Warm | Result |
|---|---|---|---|
| `SELECT COUNT(*) FROM songs` (covering autoindex on key) | 1.564 s | 0.017 s | 645 025 |
| `SELECT coalesce(sum(n),0) FROM source_songs` | 0.001 s | 0.000 s | 645 022 |

I1195 measured 4.5 s for the same COUNT on the Mac under load. The songs table has no narrow index, so COUNT(*)
has no cheap path in sqlite.

## Options

**Own lane for aggregate reads (second connection + thread).** Would let interactive reads run beside the count.
Cost: sqlite is built `SQLITE_THREADSAFE=0`, so a second thread on sqlite is not allowed, and the Amiga build has no
threads for it. Gap: the count still costs seconds of disk I/O and destroy still waits for it. Rejected.

**`sqlite3_interrupt` at destroy.** Would cut shutdown short. Cost: worker requests are not classed read/write, so an
interrupt can cancel a job-thread write (scan, import) that happens to be in flight; under THREADSAFE=0 the flag set
from another thread is a race. Gap: does not help interactive reads queued behind the count at startup. Rejected.

**Maintained counter (chosen).** Schema v8 (schema.c SCHEMA_V8) already keeps `source_songs(source, n)`, updated by
the `songs_source_ai/ad/au` triggers on every insert, delete and source change. The sum over its rows is the exact
song count, one page of a small table, the same number the Sources page shows per source. Cost: none at runtime; the
count no longer depends on catalogue size. Gap: only as correct as the triggers (see Found). The srcmirror.c snapshot
was not used: it also counts songs from an attached idx database, and the total is main-only.

## Fix

src/library/db/folders.c `SEL_USER_LIBRARY_COUNT`: `SELECT coalesce(sum(n), 0) FROM main.source_songs`. The I936 test
knob `SELECTA_LIB_COUNT_SLOW_MS` stays. engine.c comment updated.

## Regression test

`engine-library-total-cost` (tests/engine/library_total_cost_test.c). Cost is measured in pages, not time: page
count is exact and machine independent, and on a cold cache every page is a disk read.

- 20 000-song generated library (`sel_library_gen`).
- `sel_library_song_total` touches at most 8 pages (sqlite3_db_status CACHE_HIT + CACHE_MISS delta). With fix: 6.
- Total equals `COUNT(*) FROM songs` (exactness).
- Reachability: engine on that library, sentinel `stats.total_reads >= 1` and `state.library_songs == 20000`, then
  destroy.

With the fix: `song_total=20000 pages=6 max=8`, `total_reads=1 library_songs=20000`, passes.

Revert check NOT RUN: the build of the reverted tree waited over 2.5 h on the ninja gate (another agent's bbmp
plugin build in worktree agent-affdffced4e614775 held it), so the agent stopped and restored the fix. To close it:
put `SELECT COUNT(*) FROM songs` back in folders.c, rebuild `library_total_cost_test`, and expect the page assertion
to fail (COUNT over a 20 000-key index touches roughly 100+ pages, against a cap of 8). Unverified.

## Found

- Drift on the real library copy: `source_songs` sums to 645 022, `COUNT(*)` gives 645 025. The 3 missing rows are
  the `testsrc` songs (ids 16876-16878). No code path writes `source_songs` outside the triggers; cause unknown,
  probably an external or test write against the real db done with triggers absent. The total shown is now 3 lower
  on that db. A one-off re-derive (`DELETE FROM source_songs; INSERT ... SELECT source, count(*) FROM songs GROUP BY
  source`) in a migration would fix it at the cost of one full scan once.
- Open: other slow reads on the worker (none measured above 100 ms here) still block destroy the same way; a general
  cancel at destroy was not done (see the interrupt option).
