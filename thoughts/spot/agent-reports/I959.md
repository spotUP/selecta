# I959: navigation turns on the real library

Branch i959 (based on a955c303). Ledger row I959.

## Summary

The numbers in the ledger row (Sources chip turn_ms_max 397 ms, opening the Modland page 233 ms) are an artefact of the scripted `--input`
mem-backend replay. That replay runs a whole script, its waits included, inside ONE desk_wait turn (TURNTRACE showed `replay=230`), so
turn_ms_max there measures the script, not a navigation turn.

Measured in the live SDL loop (`--backend sdl`, `SDL_VIDEODRIVER=dummy`, `SELECTA_SDL_TEST_LIVE=1`, timed mouse events) on a copy of the
real library (516k Modland songs, 780 MB), prefs `library.sync_stale_days=0`:

| Action | turn_ms_max | pump_ms_max | Phase |
| --- | --- | --- | --- |
| Sources chip, 5 steps | 7 | 1 | n/a |
| Sources chip, then Modland sidebar row | 25 | 1 | n/a |
| Browse, then Modland source tile | 40 | 1 | desk_present (draw) |

All are under the 50 ms bound; the Modland tile draw at 40 ms is the closest.

## The real defect

A Browse format tile (for example Impulsetracker) runs a search with a large result. On the UI thread, `view_source_apply` calls
`search_reload` and `search_pick_songs`; those and the QUERY view insert loop, `cmd_QUEUE_ADD_QUERY` and `cmd_PLAY_QUERY` fetched each row key
with `sel_engine_result_key(e, i)` (src/engine/engine.c), which rescans res_text from the start with strlen for every row. That is O(n^2).

Measured pump_ms_max on a synthetic Modland fixture, unfixed code: 19 s at 100000 songs, 62 to 77 s at 200000 songs. A macOS `sample` of the
process showed `sel_engine_pump > view_source_apply > _platform_strlen`.

## Fix

src/engine/engine.c: in-order key pointer walks (`key += strlen(key) + 1u`) replace the per-row `sel_engine_result_key(e, i)` in
`view_source_apply` (query branch, qview insert loop), `cmd_QUEUE_ADD_QUERY`, `cmd_PLAY_QUERY`, `search_pick_songs` (first/next pointer
arrays) and the `search_reload` main loop. Each site carries an I959 comment.

After: 50000 songs, format tile turn_ms_max 5, pump_ms_max 4; 200000 songs pump 74 s to 73 ms.

## Test

`dui-nav-turn-cost` (tests/dui/nav_turn_cost.cmake) drives the real SDL loop with timed events on a 50000 song fixture: Sources chip then
Modland row; Browse then format tile; Browse then Modland source tile. It asserts turn_ms_max < 50 and pump_ms_max < 50 (best of up to 3
runs, because wall-clock numbers jump on a loaded machine; a regression is seconds in every run) and checks sentinels that the chip and pages
really opened. Revert proof: with engine.c from HEAD the run fails with "browse-then-format-tile: pump_ms_max is 19371, want < 50"; with the
fix it passes. The Modland source tile does not run a search, so the format tile is the case that guards the fix.

## Open items

- `search_reload` is still linear: about 0.35 ms per 1000 songs, 73 ms at 200000 songs on the UI thread. Moving it off the UI thread or
  capping the rows is a separate row.
- `sel_engine_result_key` itself is still O(i); other callers (apps/selecta-cli/main.c:455, analyse.c:228, library.c:213) were not touched.
- The 40 ms Browse then Modland tile draw on the real library (desk_present) is the closest turn to the limit.
- I906h online scope still needs a live network run.
- The premise of ledger row I959 (397 and 233 ms on the real db) should be corrected: those are scripted-replay numbers.

## Neighbouring tests

On build/sdl: dui-browse-tiles, dui-browse-modland-tile, dui-collection-page, dui-source-drill pass with the fix. dui-search (golden hash), dui-search-online (Radio stream) and dui-search-dblclick (selecta-test.mod missing from the fresh build tree) fail; dui-search and dui-search-online fail identically with engine.c from HEAD, so they are not caused by this change.
