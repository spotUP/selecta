## I1254 prefix vs suffix: NOT REPRODUCIBLE as stated; no fix, no test (a test would pass before and after)

Every place that reads an Amiga file-name prefix (grep of src, plugins, apps; the nuade, uade and hively probes do not read the name at all):
- src/engine/claims.c sel_registry_claims_name (browse listing predicate): returns 1 if the last extension OR the prefix is in some plugin's SEL_RP_EXTENSIONS. A claimed suffix already makes the name claimed; the prefix only matters when the suffix is unclaimed. The result is boolean, so "suffix wins" is already the effective rule.
- src/platform/platform.c sel_platform_of_name (cover family): tries the last extension first, prefix only when the suffix has no row. tests/dui/cover_unit.c covers it.
- Open path: engine.c find_replayer calls every plugin's content probe with the name; no probe reads the prefix. tests/m3/hively_decode.sh already proves `ahx.raining stars` and `raining stars.ahx` both play.

Invariant (holds today): a claimed suffix is never overridden by a prefix.

Root cause of the I1242h/I1242k symptom: the format-audit tooling picked `ay.pt3` and `mp2.usflib` as samples of ext ay / mp2 (audit doc line 14: samples "found by loose matching" of prefix-style names). The real causes:
- `ay.pt3` is a ProTracker 3 ZX file: only plugins/replayers/zxtune claims pt3, and it builds only with SELECTA_ZXTUNE_SRC (not in tree), so open correctly gives no_replayer.
- `mp2.usflib` is a USF library companion file, claimed by no replayer (not a song).

Side effect worth a decision (not changed): the browser lists `ay.pt3` / `mp2.usflib` as playable because the prefix `ay` / `mp2` is claimed. This cannot be fixed in claims.c without a table of all known extensions (the registry only knows built plugins), so a real rule needs a design decision.

## I1255 MAX.AlloAllo level5: SAMPLE IS DAMAGED, parser is right; no fix

Fetched https://modland.com/pub/modules/Maximum%20Effect/Old%20%20Tramp/MAX.AlloAllo%20level5 (9264 bytes, sha256 dc4297fd4bd3a79e76d686a1a7d9da7a71241e49652219ffac390a625c11b650). Header bytes: `2d2d2d0f 2d2d2d14 00000140 0000026c ...`. 0x2d is '-': the first three bytes of the first two longs were overwritten. With those 6 bytes set to 0 (words `0000 000f`, `0000 0014`; 0x14 = RECORD_FIRST 2 + 1 record * 0x12) the unmodified third_party/nuade/players/maximumeffect/mxe_module.c mxe_module_parse accepts it (1 subsong); the file as shipped is refused (checked with a host probe linking mxe_module.c). The rest of the file (lists at 0x140, 0x26c, 0x398, 0x4c4) is consistent. So it is a corrupt Modland file, not a parser bug. The row can close as "bad sample".
