# Selecta M4: ARexx port

Implements design doc `thoughts/shared/plans/2026-10-22-architecture-design.md` D7 (line 552), section 16 (line 458: "an ARexx port maps 1:1 onto the same commands so HippoPlayer-style ARexx scripts port by renaming the port"), the reflection and atomic-list bullets of the protocol additions (lines 185, 190), the song-change hook (line 194), the layout line `plugins/scripting/ arexx/ (amiga)` (line 474) and the M4 row (line 520). M1.2 names the ARexx port as the Amiga equivalent of the control socket (`2026-10-23-m1-2-playlists-views-control.md:53`, `:143`).

## 1. Goal and finish line

Any Amiga program (ARexx scripts, Amarchy, Directory Opus, HippoPlayer scripts with the port renamed) controls everything in Selecta through a public ARexx port, and reads results back in `RESULT`.

Finish line: on the Replay Amiga, with Selecta running the text UI, an ARexx script run through the amiga MCP (`amiga_rexx`):
1. finds the port `SELECTA` (`amiga_arexx_ports`);
2. sends `OPEN <mod>`, `PLAY`, `VOLUME 40`, `STATUS`, and gets `RC=0` for each;
3. reads back a `STATUS` result with `state=playing`, the song title, and `volume=40`;
4. reads back `COMMANDS` with 103 or more lines (one per verb in `commands.def`, counted from the generated table, not grepped);
5. gets `RC=10` and an error text in `RESULT` for an unknown verb;
6. sends `QUIT`, after which the port is gone and the process has exited.
Selecta's `--stats` output shows `arexx_cmds=N`, the sentinel that the port code ran (same pattern as `socket_cmds`).

## 3. Shared reply layer (host and Amiga)

One function turns a protocol line into a reply, used by the socket, the ARexx port and `selecta-cli`:

`int sel_ctl_exec(sel_engine* e, const char* line, char* reply, size_t cap, int* rc)` in `apps/common/ctlexec.c` (lifted out of `ctl_handle` in `apps/selecta/main.c`, not copied). It sends the line, pumps the engine, and builds the reply from the events of that line:
- error: first `ERROR` event, `rc = 10`, reply `<code> <text>`;
- result: the `RESULT` events of that line, one per output line, joined with `\n`, `rc = 0`;
- otherwise `rc = 0` and an empty reply (the socket still writes `OK`, so current clients do not change).

New event `RESULT "s"` in `events.def`: one line of a command's answer. `COMMANDS`, `EVENTS`, `TAGTYPES` and `STATUS` emit `RESULT` lines instead of `LOG` lines. The socket reply becomes `OK` followed by the result lines and a closing `.` line (the mpd and SMTP convention), only for verbs that emit results. A reply that does not fit `cap` ends with `ERROR result_truncated`, never silently cut.

Limits (the code decides today's, the plan sets the new ones):
- `RESULT` lines are copied into the reply as they are pumped, never held as pointers: `emit_log`'s ring of 8 slots of 96 bytes (`engine.c:617`) cannot back 103 lines. A `RESULT` line is at most 255 bytes; the longest `COMMANDS` line is measured from the generated table (M4-AX-1-4) and the test fails if it is over 255.
- Reply cap `SEL_CTL_REPLY_MAX` is 16384 bytes for the socket and the ARexx port (today 1024, `ctlsock.c:113`). `COMMANDS` is about 7 KB, so the cap is at least twice the measured size; M4-AX-1-4 measures it and fails if `COMMANDS` takes more than half the cap.
- Request line limit stays 1024 bytes (`ctlsock.c:14`, the pool in `ctl_handle`). A longer ARexx `ARG0` is refused with `RC=10`, `overflow`, never cut.
- The engine event queue (256 by default, `engine.c:5011`) must hold one command's results: `sel_ctl_exec` pumps after the line and again until the queue is empty; a command that emits more than 256 events is a defect found by M4-AX-1-4, not handled by dropping.
- When a line yields both an `ERROR` and `RESULT` lines, the error wins: `rc = 10`, result lines dropped.
- Verbs are matched as the codec matches them today (exact table lookup); M4-AX-1-4 states whether `play` in lower case is accepted, from the code, and the port does not add its own case folding.

## 4. Protocol additions

### 4.1 STATUS

`STATUS` (no arguments, area `protocol`) emits one `RESULT` line per field, `key=value`, from `sel_engine_state`:
`state=playing|paused|stopped`, `title=`, `composer=`, `path=`, `subsong=n/m`, `position_ms=`, `duration_ms=` (0 when unknown), `volume=0-100`, `repeat=off|all|one`, `random=on|off`, `queue_pos=n/m`.
Values are not quoted; a value ends at the end of the line. ARexx scripts parse it with `PARSE VAR`.

### 4.2 QUIT

`QUIT` (area `protocol`) asks the shell to end the run the same way the text UI's quit key does (same exit path, same stats output). Over ARexx the port replies first, then closes. The engine has no quit path today, so `QUIT` sets a flag in the engine that the shell loop takes between turns with `sel_engine_take_quit`, the same way it takes `sel_engine_take_ui_switch` (`apps/selecta/main.c`, after the UI waits); the loop then ends as if the primary UI had returned -1. `QUIT` inside a `BEGIN` block takes effect at `END`. The reply of the `QUIT` line itself is `rc=0`, sent before the loop ends.

### 4.3 COMMANDS, machine-readable (Amarchy request, 2026-10-25)

`commands.def` gets two columns: `SEL_CMD(id, args, area, argnames, label)`, for example `SEL_CMD(VOLUME, "i", "transport", "level", "Volume")`. A build-time check fails when a verb has no label or when the number of argument names does not match the argument letters.

`COMMANDS` emits one `RESULT` line per verb: `VERB [argname ...]<TAB>Label<TAB>args=<letters> area=<area>`, for example `VOLUME level\tVolume\targs=i area=transport`. The first two fields are the format Amarchy asked for (`VERB [arg-name ...]`, tab, label), so its menu rows take their labels from the port. The third field keeps the signature and area that the command palette and the help overlay already read. Optional arguments are written `[name]`, repeating ones `name...`.

Labels are full English words (global rule): `Previous Album`, not `Prev Album`.

## 5. ARexx port (Amiga)

`plugins/scripting/arexx/` (design doc line 474), a scripting plugin built only for `__amigaos__`, opened by the shell at start when `rexxsyslib.library` opens; without it Selecta runs on with `arexx=off` in the stats output.

- Port name: `SELECTA`. When `FindPort("SELECTA")` finds one (a second Selecta), the next free name `SELECTA.2`, `SELECTA.3`, up to `SELECTA.99`; past that the port stays off and the stats show `arexx=off`. Names are taken in order, so when `SELECTA` closes and `SELECTA.2` stays, the next new instance takes `SELECTA` (the free name with the lowest suffix). The stats output shows the name in use as `arexx_port=SELECTA.2` (HippoPlayer and AmigaAMP practice). Created with `CreateMsgPort` plus `AddPort` inside `Forbid`/`Permit` after the `FindPort` check.
- Each turn of the shell loop: `GetMsg` until empty. For each `RexxMsg`: `ARG0(msg)` is the line; `sel_ctl_exec` runs it; `rm_Result1` = `rc`; when `RXFF_RESULT` is set and `rc == 0`, `rm_Result2 = CreateArgstring(reply)`. `ReplyMsg`. When `RXFF_RESULT` is not set the reply text is dropped and `rm_Result2 = 0`.
- RC codes: 0 OK; 10 the command failed (codec or engine `ERROR`; text `<code> <text>`, for example `unknown_command FOO`, `argument_count`, `empty_line`, `overflow`, `idle_not_supported_over_arexx`); 20 the port is closing (`port_closing`). No other values.
- Where the error text goes is NOT yet decided: in ARexx, a non-zero primary result makes the interpreter read `rm_Result2` as a secondary error number, not as a string, so `RESULT` may stay unset when `RC=10`. M4-AX-0-3 measures this on the Replay Amiga before M4-AX-3-1 is written; finish line step 5 depends on it (open question 6).
- Counters: `arexx_cmds` counts replies with `rc == 0` (same as `socket_cmds`, which counts only `OK` lines, `apps/selecta/main.c:233-235`), `arexx_errors` counts the rest. Both are printed with `--stats`.
- Concurrency: the port is served in the shell loop after the UI waits and the engine pump, in the same thread, so a message never runs while a UI handles a key or a mouse event; the GUI sees the result at the next turn. A message that arrives while a slow command runs (for example `OPEN` of a large file) waits unreplied: ARexx has no timeout of its own and the sender blocks. Its worst case is measured in M4-AX-5-4. At most `AREXX_MSGS_PER_TURN` messages are taken per turn so a script loop cannot starve the UIs (open question 7 sets the number).
- `IDLE` over ARexx would hold the message and block the caller's script: it replies `RC=10` with `idle_not_supported_over_arexx`. The check is in the port before `sel_ctl_exec` (the engine has no `IDLE` handler today, section 2); it is matched on the verb after the codec has parsed the line, so `idle` spelled any way the codec accepts is refused. Scripts that wait for a song change use the hook (M4-AX-4-2) or poll `STATUS`.
- `BEGIN` / `END` (design doc line 190): the engine's batch flag is engine-wide (section 2), so the port does not keep a private queue. Each line is a separate message with its own reply; lines between `BEGIN` and `END` are held by the engine and applied at `END`. Two clients that interleave inside one `BEGIN` share the batch. When the port closes with a batch open it runs `END` first. What a second `BEGIN` or an `END` with no `BEGIN` answers is measured from the engine in M4-AX-3-3 and written into the test, not invented. Open question 8 asks whether Johan wants this or a per-client batch.
- At exit: `RemPort`, then reply every queued message with `RC=20` and `port_closing`, then `DeleteMsgPort`. No message is left unreplied (an unreplied RexxMsg hangs the sender). The same close runs on every way out of the shell loop: `QUIT`, the UI's quit key, a UI failure return, and the Ctrl-C path (`75238b0`). A message that arrives between `RemPort` and `DeleteMsgPort` is possible only inside `Forbid`; the close does `Forbid`, `RemPort`, drains with `GetMsg`, `Permit`.
- Arguments with spaces: the line is parsed by the same codec as the socket, so `OPEN "DH0:Music/my song.mod"` works as on the socket. The whole command is the single string in `ARG0`; the script quotes it for ARexx (`ADDRESS SELECTA 'OPEN "DH0:Music/my song.mod"'`). A path with `"` or `\` is escaped as the codec does (`src/core/codec.c:138-157`); `dist/amiga/rexx/` documents this in a comment. A port message that is not a command (`RXFUNC`) or has an empty `ARG0` replies `RC=10`.
- Startup order: `rexxsyslib.library` opens, then the port is added after the engine is created and before the first UI turn, so a script that finds the port can send at once. `RexxMast` need not be running for the port; it is needed only for `rx` (the hook), and a hook that cannot start is a `LOG` line, never a shell failure.

## 8. Open questions for Johan

1. Port name `SELECTA`, then `SELECTA.2` and up for further instances. Trade-off: matches HippoPlayer and AmigaAMP practice; a mixed-case name such as `Selecta` would need quoting in scripts.
2. Socket replies with result lines end with a `.` line. Trade-off: existing clients that read one line still work for verbs without results; a JSON reply would be easier to parse on the Mac but awkward in ARexx.
3. Labels live in `commands.def` (one source of truth for every client). Trade-off: 103 labels to write once; keeping them in the desktop action table would leave ARexx and Amarchy without labels.
4. `IDLE` refused over ARexx; scripts use the hook or poll `STATUS`. Trade-off: no blocked senders; a script cannot wait for an event in one call.
5. No Selecta MCP server. On the Amiga, the amiga MCP's `amiga_rexx` drives the port directly. On the Mac, `selecta-cli send` over the control socket does the same from a shell. Trade-off: no new server to maintain; a Selecta MCP would give typed tools (play, status, wait for event) usable from any Claude session without a shell.
6. Error text over ARexx. If M4-AX-0-3 shows that `RESULT` is not set when `RC=10` (the usual ARexx rule), the finish-line step 5 cannot read the text in `RESULT`. Recommended: `RC=10` with a numeric `Result2` (the error's index in a fixed list) plus a `last_error=<code> <text>` key in `STATUS`, so a script reads the text with one more call. Trade-off: one extra call after a failure; the alternative, returning the text as `RC=0` with an `ERROR ...` string, makes every script test the text instead of `RC`.
7. Messages taken per shell turn. Recommended: 8 per turn (160 per second at the 20 ms turn). Trade-off: a script loop cannot starve the UIs; a burst of 100 commands takes 12 turns (about 250 ms). Taking all queued messages is simpler but lets one script freeze the screen.
8. `BEGIN`/`END` over ARexx. Recommended: pass through to the engine's one global batch, close-time `END` (section 5). Trade-off: no new state, but two scripts that interleave share one batch and a script that dies after `BEGIN` leaves the batch open until the next `END` or until Selecta exits; a per-client batch needs the engine to track a client id, which no transport has today.
9. Song-change hook scope. Recommended: Amiga only (`rx <script>`), host later with the Lua plan. Trade-off: the `hook_command` option key is declared but unused on every host today; wiring it on the Mac too is small but needs a decision on what runs (a shell command) and a security note, and is outside what Amarchy asked for.

## 8a. Answers (Johan, 2026-10-25, I342)

- Q6: `RC=10` with a numeric `Result2`; scripts read the error text through a `last_error=` key in `STATUS`. M4-AX-0-3 still measures the Replay behaviour first.
- Q7: 8 messages per shell turn.
- Q8: `BEGIN`/`END` pass through to the engine's one global batch; the port sends `END` when it closes.
- Q9: the song-change hook is Amiga only (`rx <script>`).
