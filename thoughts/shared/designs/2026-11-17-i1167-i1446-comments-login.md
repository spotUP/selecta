## 1. Song key comments attach to

Key = `(md5, subsong)`: md5 of the file bytes (same hash as loudness and the catalogues), subsong = 0-based
tune index (SID, multi-song formats; 0 for single-song files). Reasons: one file reached through Modland, HVSC,
AMP, a local folder or the NAS gets the same thread; paths differ per source and per mirror, bytes do not.

- Songs with no md5 yet (local file never hashed, stream): Selecta hashes the file on first open of the comment
  panel (one md5 pass, already done for loudness). Streams with no file (radio, YouTube) get no comments in v1.
- Rips that differ by a byte split the thread. Accepted for v1; a server alias table (`song_alias(md5, canon_md5)`)
  can merge them later from the existing Selecta duplicate pick (`dup_pick`) without a client change.
- Timed position: milliseconds from the start of that subsong. Loop-forever formats: position is played time, so
  a comment at 5:10 on a 2:40 loop shows at 2:30 too only if the client folds it; v1 shows it at its raw time
  and the waveform/progress bar caps at the known length (songdb length).

## 3. Server API (all under `https://hippoplayer.se/cygnus/api/v1`, JSON, rate-limited)

Comments (read is public, `optionalAuth` adds `mine`/`reported` flags):
- `GET /comments?md5=&subsong=&after=&limit=50` thread page, newest first, replies nested one level.
- `GET /comments/timed?md5=&subsong=` all visible timed comments, compact (`id, position_ms, user, body`),
  ETag; this is what the play view fetches when a song starts.
- `GET /comments/counts?md5=a,b,c` comment counts for a list view (up to 200, like ratings batch).
- `POST /comments` (auth) `{md5, subsong, position_ms?, parent_id?, body}`; `PATCH /comments/:id`,
  `DELETE /comments/:id` (own only, or moderator).
- `POST /comments/:id/report` (auth) `{reason}`.

Auth (extends `AuthRoutes.ts`, keeps `/login` and the 30 d JWT working for DEViLBOX):
- `POST /auth/device` `{platform, device_name}` -> `{device_code, user_code, verification_uri, interval, expires_in}`.
- `POST /auth/device/token` `{device_code}` -> 428 pending / 200 `{access_token, refresh_token, user}`.
- `POST /auth/login` gains `refresh: true` -> also returns a refresh token (Mac/Linux/Windows password path).
- `POST /auth/refresh` `{refresh_token}` -> new access token plus rotated refresh token.
- `GET /auth/devices`, `DELETE /auth/devices/:id` (sign out a device; the web account page lists them).
- `POST /auth/signup` opened to the web sign-up page on hippoplayer.se (captcha or proof-of-work plus rate limit),
  still accepting the DEViLBOX forward.

Artists and notifications (auth):
- `GET /artists/search?q=`, `POST /artists/:id/claim {method, evidence}`, `GET /me/claims`.
- `GET /notifications?since=<id>` (ETag, 304 when nothing new), `POST /notifications/read {up_to}`.
- Moderator only: `GET /mod/queue`, `POST /mod/comments/:id {state}`, `POST /mod/claims/:id {state}`.

## 4. Persistent login

Goal: sign in once per device, never asked again unless the user signs out or revokes the device on the web.

- Two tokens. Access token: JWT `{userId, deviceId, scope}`, 1 hour. Refresh token: 256-bit random, stored as
  sha256 in `user_devices.refresh_hash`, no fixed expiry; expires only after 1 year without use, or on revoke.
- Rotation with a grace slot: each refresh returns a new refresh token; the previous one stays valid
  (`prev_refresh_hash`) until the new one is used once. A dropped reply on a flaky Amiga link therefore never logs
  the device out. A refresh with a token older than prev means theft: revoke the device.
- Offline: the client keeps the refresh token and retries with the existing backoff (`net/backoff.c`); a server
  outage never deletes local credentials. Only an explicit 401 `device_revoked` signs the client out.
- Client module: extend `src/library/net/devilbox.c` (rename later is cosmetic) with refresh, device flow and a
  storage seam `sel_secret_get/put/del(name)` in `src/core/<os>/secret.c`; the existing 0600 file is the default
  backend and the posix fallback.

Secure storage per platform:

| Platform | Store | Notes |
|---|---|---|
| macOS | Keychain, generic password, service `se.hippoplayer.selecta` (Security.framework `SecItemAdd/CopyMatching`) | Migrates `devilbox.token` once, then deletes the file |
| Linux | libsecret (Secret Service) when a session bus answers, else `~/.config/selecta/account.token` 0600 | Headless/text UI boxes usually take the file |
| Windows | Credential Manager (`CredWriteW`, DPAPI underneath) | |
| Amiga | `ENVARC:Selecta/account.token` (copied to `ENV:` at boot) | Risk below |

Amiga risk: any program and any user of the machine can read ENVARC, there is no memory protection, and with
no AmiSSL every request goes over plain http, so the access and refresh tokens are readable on the LAN path to
hippoplayer.se. Mitigations: Amiga devices get scope `amiga` (comment, report, notifications, ratings; no
password change, email change, device list, account delete), device shown on the web as "Amiga, plain
connection" with one-click revoke, never a password typed on the Amiga, and when AmiSSL is present
(`sel_tls_available()`) the https base is used as on desktop. The token file is written with
`FIBF_READ`-only protection bits (cosmetic, not security).

## 5. Sign-up and login from inside the app

Device code flow (RFC 8628) is the one flow on every platform:
1. User picks "Sign in" (Account page, comment composer, or the welcome card, section 8).
2. App calls `POST /auth/device`, shows `hippoplayer.se/link` and an 8-letter code (`WDJB-MJHT`), plus a QR code on
   Mac and the desktop UI (the text UI and MUI show the code only).
3. User opens the URL on any phone or computer, signs in or creates an account there (the web page owns sign-up,
   captcha, email, password reset), types or confirms the code.
4. App polls `/auth/device/token` every `interval` (5 s, Amiga 10 s) for at most 10 minutes, stores the tokens,
   shows "Signed in as <name>".

Mac, Linux and Windows also open the URL in the default browser with the code prefilled. Password login inside
the app stays as a fallback on platforms with TLS (Mac, text UI on desktop): reuses `sel_devilbox_login` with
`refresh: true`. No password field ever exists in the Amiga UI. The CLI keeps `selecta-cli devilbox login`
and gains `selecta-cli account link` (device flow).

## 6. Artist verification

A verified artist account is linked to one or more `artists` rows; every song whose md5 maps to that artist in
`song_artists` pings the account on new comments and replies.

Methods considered:

| Method | Proof strength | Effort | Verdict |
|---|---|---|---|
| Code in a Demozoo scener page | None: Demozoo pages are editable by any Demozoo user | Low | Reject as proof |
| Code in a CSDb scener/user profile | Medium: CSDb profile text is owned by the linked CSDb user, but most sceners have no CSDb login | Low | Accept as one evidence item |
| Code on an own web page, Bandcamp, SoundCloud, Mastodon or GitHub profile already linked from the Demozoo/CSDb/DeepSID entry | Good: the link predates the claim | Low | Accept as evidence, auto-checked by the server |
| Email from an address published in the scener's Demozoo/CSDb profile | Good | Medium | Accept as evidence |
| Manual review by a moderator (Johan) with any of the above, or personal knowledge | Best | Johan's time | Final step |

Recommendation: claim form plus manual approval. The user searches an artist (one search over the `artists`
table built from HVSC, Modland, Demozoo and CSDb), presses "This is me", picks evidence: a profile URL already
linked from that artist's Demozoo/CSDb entry where the server finds the claim code, or free text. The server
auto-checks URL evidence and marks the claim "evidence found"; a moderator approves in the web queue in one
click. Volume is small (scene composers), so manual approval is cheap and blocks impersonation, which matters
because a verified badge appears next to comments. Pending claimants get no pings and no badge.

## 7. Notifications

- Kinds: comment on a song of an artist you verified as; reply to your comment; claim approved/rejected.
- In-app inbox: bell icon with unread count (Mac rich UI and desktop UI), "Inbox" entry in the text UI menu and the
  MUI menu; each item opens the song and scrolls to the comment (timed comments seek on click).
- Polling: on start, then every 15 minutes while running on desktop, every 30 minutes on the Amiga, and on opening
  the inbox. `GET /notifications?since=` with ETag, 304 when nothing new, so a poll is about 200 bytes. No push
  channel in v1 (no websocket, Amiga cannot hold one cheaply).
- Grouping: several comments on one song since the last read collapse into one entry ("3 new comments on X").
- Email: optional, off by default, needs the web page to collect and verify an email; daily or weekly digest only,
  never one mail per comment. Server sends through a transactional SMTP relay. Ships after the inbox (row C7).

## 8. Optional login, unlocks and gentle encouragement

Logged out keeps every current feature: playback, library, all sources, search, playlists, local ratings, art.
Reading comments logged out: recommended YES. The thread and the timed markers are public (Johan: "everyone
could see the comment"), and seeing the conversation is the strongest reason to sign in. Logged out users see
comments read-only; the composer shows "Sign in to join the conversation".

Candidate unlocks:

| Unlock | Exists today | v1 |
|---|---|---|
| Post comments, timed comments, replies | no | yes |
| Report comments | no | yes |
| Artist verification, badge, pings on your songs | no | yes |
| Notification inbox | no | yes |
| Ratings synced to hippoplayer.se (shared with DEViLBOX) | yes (CLI login only, I173) | yes, exposed in the GUI |
| Hippo votes and loudness/lyrics contributions under your name | partly (server tables exist) | no, later |
| Favourites synced across devices | no | later (needs a sync design: conflicts, Amiga) |
| Playlists synced across devices | partly (playlist API `/api/v1/playlists`) | later |
| Public profile page (comments, favourites, artist page link) | no | later |
| Listening stats / year review | no | later |
| Follow an artist (pings on new songs in the catalogues) | no | later |

Recommended v1 set: the first five rows. They all ride on one auth path and one inbox; sync features each need
their own conflict design and would double the scope.

Encouragement without nagging:
- Never a modal and never at start-up. No timer that pops a prompt.
- Point of use only: the comment composer, the report button and the "This is me" artist button show an inline
  "Sign in" button where the action would be. The comment count badge on the play view is visible logged out.
- One welcome card on Home after the user has played 20 songs, offering sign-in with the unlock list; "Not now"
  hides it for 30 days, "Do not show again" hides it for good. Shown at most 3 times in total.
- Account page in Settings always has the Sign in button and the unlock list.
- Signed-out state never shows a badge, a red dot or a count that only signing in clears.

## 9. Moderation

- Report button on every comment (signed in only). Distinct reporters count; accounts younger than 24 h count 0.
- Auto-hide at 3 distinct reports (state `hidden`, report author still sees it as "Hidden pending review"); the
  moderator queue restores or removes. Hidden comments return 404-free placeholders in threads so replies keep
  their context.
- Spam control: `express-rate-limit` per user (10 comments / 10 min, 100 / day) and per IP; body length 2000;
  new accounts under 24 h limited to 3 comments; link text not rendered as links in v1.
- Verified artists may hide (not delete) comments on their own songs: open decision D5.
- Account delete removes comments through the existing `ON DELETE CASCADE` (or anonymises them: decision D6).

## 10. UI per track (outline)

Mac rich UI (Spotify reference design):
- Play view: timed comment markers above the progress bar (avatar dots, clustered when dense); hover shows the
  comment, click seeks; while playing, a comment fades in near the bar as its time passes (toggle "Show comments
  while playing", default on).
- Song Information gets a Comments tab: thread, replies, composer with "at 1:23" toggle (uses current position).
- Track lists: optional comment-count column.
- Bell + inbox popover in the top bar; Settings > Account (sign in via device code + QR, signed-in name, devices
  link to the web, unlock list, artist claims and their state, email digest setting link).
- Artist/composer page: "This is me" button; verified badge.

Text UI: Comments pane (thread, timed comments listed with their time, Enter seeks), compose line, Inbox menu
entry, Account menu with the device code shown as text, `c` key on the play view opens Comments.

Amiga MUI (MUI 3.8, 1:1 with Mac per the MUI parity rule): Comments page in the Song Information window
(NListview thread + String gadget composer + "at current time" checkmark), timed markers as ticks drawn in the
position gauge subclass, Inbox window from the menu with unread count in the title, Account window with the
device code in large text. AGA/RTG desktop UI: same widgets as the Mac desktop UI. Network on Amiga goes through
`src/core/amiga/net.c` over plain http unless AmiSSL is present; all fetches are asynchronous off the engine
idle tick (same rule as I1003b). Timed comments for the current song: one `/comments/timed` fetch per song start,
cached in memory for the session, capped at 500 entries per subsong on 68020.

## 12. Open decisions for Johan

- D1 Read comments logged out. Recommended: yes, read-only. Trade-off: public reading drives sign-ups and matches
  "everyone could see"; the cost is that hidden-pending-review spam is briefly visible to anyone.
- D2 v1 unlock set. Recommended: comments + replies + timed comments, report, artist verification + pings, inbox,
  ratings sync in the GUI. Trade-off: synced favourites/playlists and profiles are attractive unlocks but each
  needs a conflict/sync design and roughly doubles the scope; later rows.
- D3 Encouragement. Recommended: point-of-use sign-in buttons plus one welcome card after 20 plays (30-day snooze,
  max 3 showings), never a modal. Trade-off: fewer sign-ups than a start-up prompt, but no nagging.
- D4 Artist verification. Recommended: claim form with auto-checked profile evidence, final manual approval by a
  moderator. Trade-off: Johan's time per claim (small volume) versus impersonation risk of a fully automatic check
  (Demozoo pages are editable by anyone).
- D5 Verified artists may hide comments on their own songs. Recommended: yes, hide only, moderator can restore.
  Trade-off: artists control their space; risk of hiding fair criticism.
- D6 Account delete. Recommended: anonymise comments ("deleted user") instead of cascade delete. Trade-off: threads
  keep their sense; user content stays (body can still be removed on request).
- D7 Amiga over plain http. Recommended: allow Amiga sign-in with a reduced-scope, revocable device token.
  Trade-off: tokens are sniffable on the network path without AmiSSL; the alternative (no Amiga login without
  AmiSSL) breaks the "Amiga for every feature" rule.
- D8 Open web sign-up on hippoplayer.se (today only DEViLBOX can create accounts). Recommended: yes, shared users
  table with DEViLBOX, captcha + rate limit. Trade-off: a public sign-up page invites bot accounts; required for
  any in-app sign-up.
- D9 Email digest. Recommended: later row, off by default, digest only. Trade-off: email reaches artists who do
  not run Selecta daily, but needs an SMTP relay, email verification and GDPR handling.
- D10 Report threshold. Recommended: 3 distinct reporters with accounts older than 24 h. Trade-off: lower hides
  abuse faster but lets 2 users silence anyone.
