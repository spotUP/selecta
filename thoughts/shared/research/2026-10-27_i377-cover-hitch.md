# I377: Amiga cover art hitch on the UI thread

## Result
- Worst single art job (`art_load`: fetch, stb decode, centre square, scale, thumb write-back) on rig 2:
  **714 ms** for 3 covers decoded (art_decodes=3, quant_calls=2), 68060 at host speed, rtg, depth 8 (`--format index8`).
- Budget: input-to-redraw at most **40 ms** on the 68020 AGA tier (m4-amiga-ui.md 4.5 / item 15; I368 reuses it).
  714 ms is about 18 times the budget on a 68060. A first attempt on the 68020 at real speed (`rig.py start --a1200`)
  never reached a decoded cover in several minutes (frames=1, art_decodes=0), so there is no 020 number.
- Verdict: **over budget**. The UI thread is blocked for the whole job; no key, mouse or redraw is served.
- `turn_ms_max=9359` in the same run is the first turn (library open, atlas, first frame), not the cover job. It is also
  far over budget but belongs to I368 / start-up, not I377.

## Method
- Measurement only, no behaviour change: the `ui_stats` line of `--stats` now ends with `art_ms_max=` (longest single
  `art_load`, host clock ms, EClock resolution on Amiga) and `turn_ms_max=` (longest `desk_wait` turn minus its poll
  wait). Tags `SEL_UI_STAT_ART_MS_MAX` / `SEL_UI_STAT_TURN_MS_MAX` (include/selecta/tags.def 0x5062, 0x5063).
- Amiga 68020 cross build (cmake/amiga-68020.cmake), put to `SYS:selecta-test/Selecta` on rig 2 (purpose "Selecta session:
  I377 cover hitch"), fixture DB with 3 embedded covers (scratchpad i369/cover.db):
  `Selecta --ui desktop --backend rtg --format index8 --stats --db RAM:cover.db --exec "QUEUE_ADD fixture/1.mod"
  --exec "QUEUE_ADD fixture/2.mod" --exec "QUEUE_ADD fixture/3.xm" --exec "QUEUE_ADD fixture/4.it" --view home
  --log RAM:cover.log >RAM:stats.txt`, then `break 7 C`, then read `RAM:stats.txt`. Rig stopped afterwards.

## Why the fix is not in this commit
`art_load` is synchronous by contract on every host (`art_thread_start` + `art_thread_join` back to back; art.h says
"the interactive backend will poll instead (DUI-P2-7)"). Moving the job off the UI thread therefore needs the polling
design, not just a task: a non-blocking `art_begin`, an `art_ready` polled from `desk_wait`, tiles redrawn when it flips,
and the cache made safe against `art_tile` reads while the worker writes (publish per album once the pixels are final).
The worker needs an Amiga process (CreateNewProc with NP_StackSize) of at least the 128 KB of amiga_start.h;
`sel_gui_image_scale` already keeps its ~165 KB canvas on the heap (9141895), stb_image needs a measured margin (use the
stack canary). The mem backend keeps a blocking wait so the goldens stay deterministic.

## Remains
1. Async art API plus an Amiga process in `plugins/ui/desktop/amiga/art_thread.c` (stack sized with the canary).
2. Regression check: the rig 2 run above must report `art_ms_max` under 40 with art_decodes unchanged.

## Rig 2 paint vs present split (I387)
- Question: is the 1953-6127 ms full repaint (I385) spent painting the canvas or in the backend present?
- Method: `desk_flush` stamps the clock at flush start. paint = frame start to flush start (desk_present, viz_tick, desk_route_input, widget draws
  into the canvas); present = flush start to end (`desk_rtg_present` with its p96 writes and palette load, plus `sel_gui_present`). New `--stats` fields
  `paint_ms_min/avg/max` and `present_ms_min/avg/max` (tags 0x5068-0x506D). Same recipe as I385 (Amiga 68020 cross build, rig 2 default 68060,
  purpose "Selecta session: I387 repaint cost probe", `Selecta --ui desktop --backend rtg --format index8 --stats --db RAM:cover.db`, key `l` 45 s after start, `break 7 C`).
- Result (060): frames=3, keys=1, page_dirty_pixels=480000, frame_ms min/avg/max = 2172 / 4233 / 6253,
  **paint_ms min/avg/max = 2170 / 4231 / 6251**, **present_ms min/avg/max = 1 / 1 / 2**.
- Reading: the time is in the paint, not the present. The backend blit (desk_rtg_present, p96_write per dirty rect, LoadRGB32 on palette change) is
  1-2 ms per frame, 0.05 percent of the frame, so no further probe inside it is needed. A full 800x600 repaint's cost is the software drawing into
  the canvas (widget draws, glyphs, covers/gradients, effects) on the 060. Next probe, if wanted: split paint by widget class or by draw primitive.

## I389 paint split (rig 2)
- Question: which widget class or draw primitive costs the 2170-6251 ms paint of a full 800x600 repaint (I387)?
- Method: `--stats` now prints a `ui_paint` line (apps/selecta/main.c) with per-primitive time and call count
  (`paint_ms_<class>`, `paint_n_<class>`; tags 0x5070-0x508x) and per-painter time (`painter_ms_<name>`; tags 0x5090+). The clock is
  millisecond-resolution only, so a primitive's time is the sum of clock deltas around each outermost call (a nesting depth guard stops double

- Top cost: the solid-colour rasterizers. fill_rect plus round_rect plus the one gradient are 4597 of the 4650 ms the primitives account for
  (99 percent); text, icons and lines are negligible. The single 800x600 canvas fill alone took 1003 ms for 480000 pixels (about 2 us per pixel,
  0.5 Mpixel/s), so the per-pixel INDEX8 store path is the unit cost. The Home content painter (draw_home) is the top painter at 10406 of
  13317 ms.
- Not explained: the primitives sum to 4650 ms, only 35 percent of the 13317 ms painters total. About 8.7 s inside the painters is spent
  outside every timed primitive (candidates: sel_gui_dirty_add region merging, clip/region setting, tile_palette quantise, task preemption by the
  emulated system, which the wall clock cannot separate). That part is unattributed; the next probe is to time those calls the same way.
- Proposed fix level: the rasterizer, not the widgets. Make the INDEX8 solid fill, rounded rect and gradient span-based (a memset or word-wide
  store per row with the palette index resolved once per colour, not per pixel) in src/gui/draw/gui_draw.c, and stop repainting the full canvas
  per frame (the page switch repaints 480000 pixels; clip to the dirty rect). Widget code stays as it is.

## I395 paint gap and cover flow cost (rig 2)

Setup: rig 2 (68060 at host speed, no 020 run possible, see below), `--ui desktop --backend rtg --format index8 --stats`, 800x600, three frames, Selecta built from this branch. New timing classes: `dirty`, `clip` (clip push/pop and region set), `palette` (cube rebuild), `quant` (tile_palette: art lookup, 8x8 scale, quantise, palette rebuild), `art` (art_tile lookup in draw_home). | image | 267 | 6 |

| text | 34 | 41 |

| dirty merge | 0 | 76 |
| clip / region | 0 | 98 |
| palette rebuild | 0 | 0 (nested in quant) |
| art lookup | 0 | 8 |
| Sum of classes | 5745 | |

Painter laps: main 9981, canvas 911, song 743, progress 673, sidebar 201, transport 101, status 10, volume 8; sum 12628 ms.

Accounted share: 5745 of 12628 ms = 45 percent. Target of 90 percent is NOT met. What the new timers rule out: dirty merge, clip and region set, palette cube rebuild and art lookup cost 0 ms (millisecond clock). Tile quantise is real: 713 ms for 2 tiles (about 350 ms per tile), the third biggest cost after fill and round. Still unaccounted: about 6.9 s inside the painter laps, almost all in the main painter. Remaining untimed candidates in the main painter: `sel_gui_text_width` measuring (called per chip, per label), `rect_hash` of the first tile (pixel read, debug hash only), layout code, and emulator preemption (cannot be separated). The next step is timing text measure and rect_hash and, if the gap stays, a sampled painter profile with the rig monitor.

Proposed fix level:
- fill and round (3.6 s, 29 percent of painter time): rasterizer level, span-based INDEX8 fills and rounded rects (I396), already proposed in I389.
- quantise (713 ms): cache level, quantise once per cover and keep the 8-bit tile in the art cache; also an algorithm change to a fixed shared palette per screen for tiles (no per-tile cube).
- gradient (999 ms for 1 or 2 calls): rasterizer level, per-row fill for vertical gradients instead of per-pixel blend.

## I396 span rasterizers (rig 2)

Change: `fill_rect_raw`, `round_rect_raw`, `round_frame_raw` and `gradient_raw` in `src/gui/draw/gui_draw.c` now work on row spans (memset for opaque INDEX8, word loop for RGBA32, a 256-entry destination-byte table for translucent INDEX8, one gradient colour and one dither set per line). Output is byte-equal: all golden hashes (testcard rgba32 and index8) pass without update. New unit test `test_span_equals_pixel` in `tests/dui/draw_unit.c` compares spans against a per-pixel reference including the `used` bitmaps. A deliberately broken memset span made 117 checks fail; the restored code passes.
