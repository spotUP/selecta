# I948: dui-direct-calls-async hits the 300 s timeout

## Status

Not fixed. The agent ran out of its tool budget after narrowing the cause. No code change is committed.

## What is slow

- Baseline ctest run on main b0155148: passed in 250.51 s, just under TIMEOUT 300 (tests/dui/CMakeLists.txt:166). The test is slow, not hung forever.
- Almost all of the time is one sub-run: the g_comp geometry run in tests/dui/direct_calls_async.cmake
  (`selecta --output null --ui desktop --backend mem --view home --canvas 1280x800 --clock fixed --stats --input sites_in.txt`,
  input `wait 3 / topbar 2 / wait 3 / browse 1 / wait 3`). It opens the composer collection page (frame trace: page=12 colkind=6).
- Env inherited at that point: SELECTA_SDL_TEST_LIVE=1, SELECTA_LIB_TEXT_SLOW_MS=300 (set in part 1, never unset), SELECTA_LIB_UI_GUARD=log,
  SELECTA_SDL_TEST_TIMED=q@5000.
- Isolated repro (copied sites.db/cfg/input, same env, nice -n 19), 8 runs: 4 still running at a 30 s alarm, others 3/7/12/13 s.
  Without nice and with another socket path: 0.2 s. The duration depends on timing, so it is a race.

## Mechanism (evidence)

- In a slow run desk_wait (plugins/ui/desktop/desktop_ui.c:14775) returns 1 every turn through desk_present; the only sleep is the
  sel_ctl_serve poll in apps/selecta/main.c:840 (about 14 ms per turn). The loop ends only when desk_wait returns -1, which needs a turn with
  nothing to present.
- A temporary print before sel_uim_update in desk_wait showed 747 turns of `pre=3f post=3f side_stale=1 side_inflight=0`:
  SEL_UIM_DIRTY_ALL is set every turn, side_stale stays 1, no sidebar read is in flight. home_sig and library_sig stay constant.
- desktop_ui.c ~14909-14911: on a page whose view source is SEL_VIEW_FOLDERS (the composer page), desk_wait sets `d->side_stale = 1u`
  on EVERY turn ("I608: the sidebar list follows the saved playlists"), not only when the playlists change.
- desktop_ui.c:10798 (sidebar draw): `if (d->side_stale && !d->side_inflight) side_lib_reload(d);`
- desktop_ui.c:10447 side_lib_reload returns early, leaving side_stale set, when `sel_engine_library_items_busy(d->engine)` is true.
  With side_inflight=0 and (in the desktop UI) sm being the only other poster, the engine items slot is busy for another reason
  (unverified: a result nobody takes, or a read slowed by SELECTA_LIB_TEXT_SLOW_MS=300).
- desk_side_settle (desktop_ui.c:11746) loops while side_stale is set, so the scripted `wait` settle never sees a quiet sidebar either.

## Likely root cause (to confirm)

The unconditional `side_stale = 1u` for FOLDERS-source pages (I608) turns a one-shot "playlists changed" signal into a permanent one.
Each turn then wants a sidebar reload; while the items slot is busy the reload is skipped and the turn stays dirty. The run ends only when
timing lets a read post, complete and be taken in a gap. The correct fix is to set side_stale only when the saved-playlist signature
changes (compare pl_hash(hv) with a stored value, the way home_sig already does), and to find who holds the items slot.

## Next steps for a new agent

1. Confirm who holds the items slot (print sel_engine_library_items_busy reason / engine stats) in the isolated repro.
2. Gate the I608 side_stale on a playlist-signature change; rerun the repro 8 times under nice (expect all well under 1 s).
3. Regression: a dui test that opens the composer page in a mem scripted run and asserts the run ends in a bounded number of
   desk_wait turns (turn_why counters from --stats), failing with the fix reverted under SELECTA_LIB_TEXT_SLOW_MS=300.
4. ctest -R dui-direct-calls-async 3 runs in a row.

## Fix

### Q1: what holds the library items slot

Nothing holds it abnormally. Only the desktop UI posts to the engine items slot (src/engine/engine.c:7739 sel_engine_library_items_post,
callers plugins/ui/desktop/desktop_ui.c side_lib_reload and sm_lib_want). The slot is the sidebar's own read, re-posted every turn:
desk_wait set `side_stale = 1u` on every turn of a SEL_VIEW_FOLDERS page (I608 block, was desktop_ui.c:14908-14910); the draw
(desktop_ui.c:10798) posted a read; desk_side_follow took it next turn, marked the page dirty, and the I608 block made it stale again.
While a read was in flight, desk_side_follow (was desktop_ui.c:10510, `side_lib_take(d) || d->side_stale`) also dirtied every turn.
The `side_inflight=0` in the 747-turn print is the moment after the take, before the next post. Measured on the mem composer run with
SELECTA_LIB_TEXT_SLOW_MS=300: sidelib_async posts 7 to 26 per run before, 2 after.

The second spin source on the same page, found while measuring (not fixed here, open): pls_reload_run sets `pls_stale = 1u` at
desktop_ui.c:4642 when sel_engine_song_briefs is deferred (nowait, library worker busy), and desk_wait (I633 block, desktop_ui.c ~14895)
redraws every turn while `pls_stale && pls_id != 0` (the composer page has pls_id 0xFFFFFFFF). Trace with SELECTA_LIB_TEXT_SLOW_MS=300 and
SELECTA_LIB_ITEMS_SLOW_MS=300: 123 of 128 present turns came from line 4642. SELECTA_LIB_TEXT_SLOW_MS is set at
tests/dui/direct_calls_async.cmake:34 and never unset, so the slowed title/group/meta reads (src/library/db/folders.c:479) keep the worker
busy during the g_comp geometry run. Root fix: make the composer/playlist page's song_briefs a posted read taken on a later turn (the I906
pattern), so a busy library does not turn every frame into a re-poll.

### Change

- desk_wait: the I608 block sets side_stale only when pl_hash of the FOLDERS view changes (new fields side_pl_sig, side_pl_sig_set).
- desk_side_follow: a stale list dirties the page only when no read is in flight (`side_stale && !side_inflight`); the take dirties
  when the read lands.

### Regression test

tests/dui/composer_settle.cmake (ctest dui-composer-settle): scan three songs, create a playlist, open Browse then the composer tile in a mem
scripted run with SELECTA_LIB_TEXT_SLOW_MS=300; asserts sidelib_async posts <= 2, sentinel plsong 1 drawn and takes >= 1.
Revert proof (fix.patch reverse-applied, rebuilt): 4 of 4 runs failed with posts 16, 7, 26, 21. With the fix: 4 of 4 passed, posts 2.

### dui-direct-calls-async after the fix (3 runs in a row, nice 19)

Run 1 passed 54.5 s, run 2 FAILED 48.6 s, run 3 passed 62.9 s (was ~250 s). Run 2 failed at direct_calls_async.cmake:161:
