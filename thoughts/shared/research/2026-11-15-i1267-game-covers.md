# I1267: game covers for songs without an album

Trigger: Johan loaded `Turrican 2 - Freedom.sap` (Atari 8-bit) and got no Turrican 2 cover. Cause: no game image source
exists in code. Covers come from MusicBrainz/iTunes (album key) and Demozoo by title+artist (I1401,
`src/library/db/art_scrape.c` `dz_step`, `sel_dz_query`); Demozoo has no commercial games.

## Decided by Johan (2026-11-15, not open)

- Amiga game images come from Hall of Light (HOL, amiga.abime.net). C64 game images come from Lemon64.
- Box scan first; no box scan: the first title or in-game screenshot is the cover.
- Game images feed the existing slide show (no new mechanism): box scan = frame 1, screenshots = following frames;
  no box scan = screenshots only. Slide speed is the existing pref `art.slideshow_seconds`.
- Game trivia/facts are shown with the game music (section 6).
- Atari 8-bit, ST, 2600, 7800, Lynx and Jaguar game images come from Atarimania (section 1a).
- HARD rule: an image from another platform is never shown; the next source for the same platform is tried (2a).
- Sections 1a, 2a, 2b, 2c, 3a were added after the first draft and sit after section 3; section 2a supersedes the
  cross-platform fallback text in sections 1 and 2.

## 1. Sources

### Blocking finding: HOL and Lemon64 refuse non-browser clients

| Source | What a plain HTTP client gets (measured 2026-11-15) |
|---|---|
| HOL `https://amiga.abime.net/games/list/?gamename=turrican` | 200, 7 KB Anubis proof-of-work page ("Access Denied" to WebFetch) instead of results |
| HOL image `.../box_preview/1501-1600/1535_preview0.jpg` | 200 `text/html` (Anubis page), not the JPEG; `.../screen/...png` gives 500 html |
| Lemon64 `https://www.lemon64.com/games/list.php?list_title=turrican` and even `/robots.txt` | 403 Cloudflare managed challenge ("Just a moment..."); a real Chrome tab also stayed on the challenge |

Both sites deliberately block automated clients, images included. Selecta (C, libcurl/AmiSSL) cannot pass a JS proof
of work or a Cloudflare challenge, and solving them by script would be circumventing bot protection, which this design
does not do. HOL robots.txt says `Allow: /`, but the Anubis wall is the operator's current answer. HOL footer:
"Content © 1998-2026 HOL TEAM - Online Amiga database © 2002-2026 HOL TEAM"
(https://amiga.abime.net/games/view/turrican-ii-the-final-fight). No terms page, API or image-use statement found
(FAQ has none; links: /faqs, /contact-us). Lemon64 terms could not be read (challenge on every page).

Consequence: HOL and Lemon64 are usable only with the operators' permission, served through our own server
(hippoplayer.se, allowlisted by them, or from a data export they agree to). Until then they are NOT usable as the
on-demand source. Recommended: ask both teams (Johan sends; draft in plain text when he wants one) and ship the
libretro-thumbnails path meanwhile so Turrican 2 gets a box today. See decision D1.

### HOL structure (read through a real browser tab, for when access is granted)

- Search: `/games/list/?gamename=<words>` lists `/games/view/<slug>`, e.g. `turrican`, `turrican-3`,
  `turrican-ii-the-final-fight`. Slug = title lower case, punctuation dropped, spaces to `-`, Roman numerals kept
  as written (`ii`, not `2`). So "Turrican 2" must be matched through the search list plus numeral folding, not by
  guessing the slug.
- Game page holds a numeric version id (Turrican II = 1535, CD32/other versions 1536, 6522) and images by bucket of
  100: `/box/1501-1600/1535_box0.jpg` (full scan, 608 KB), `/box_preview/1501-1600/1535_preview0.jpg` (small),
  `/screen/1501-1600/1535_screen0.png` (title, then in-game), `/screen_preview/...`, plus `/disk/`, `/misc/`,
  `/sprite/`. Turrican II page: 11 box, 190 screen images (all versions).
- Use: `box_preview` or `box` index 0 for frame 1 (front cover), then `screen0..screen6`. Facts on the page: year,
  publisher, developer, credits, genre, trivia text, ratings.

## 2. Song-to-game mapping

What Selecta has (songs table: `name`, `artist`, `album`; `art_song_meta` in `src/library/db/art.c:211` reads
name+artist): `album` is filled from `SEL_META_RELEASE` (`src/library/sources/local.c:165`), which the snsf, qsf,
libvgm (VGM/VGZ game field) and minimp3 adapters emit. Whether the SID, SAP, NSF, GBS, SPC adapters fill RELEASE was
not verified (grep found only those four).

Game name, first hit wins:
1. `album` when the song's platform family is a game platform (RELEASE is the game for VGM/SPC/NSF families).
2. Title `"<Game> - <Track>"`: split on the FIRST `" - "`, left side is the game ("Turrican 2 - Freedom" -> "Turrican 2",
   "Metroid - Brinstar Theme" -> "Metroid"). No separator: whole title is the game candidate only for game
   platforms with no artist match elsewhere (keeps "Freedom" alone from matching a random game).
3. File name without extension, same split (local files without tags).
4. UnExoticA path folder (Game/<artist>/<game>/file): the game folder. Modland paths carry artist, not game: skip.

Matching (server side): lower case, drop punctuation and parenthesised tags, inverted article back to front,
Roman/Arabic numeral folding (`2` = `ii`, up to `x`), then exact; else prefix match on whole words ("turrican ii"
matches "turrican ii the final fight"); several hits: shortest name, then region Europe > USA > World > other.

Platform: `sel_platform_of_ext` family of the song (`include/selecta/platform.h`). Family -> systems: AMIGA -> HOL
(when allowed) else libretro "Commodore - Amiga"; COMMODORE_64 -> Lemon64 (when allowed) else "Commodore - 64";
ATARI -> "Atari - 8-bit Family" then "Atari - ST"; ZX_SPECTRUM, NES, SNES, GAME_BOY, MEGA_DRIVE, SEGA_MASTER_SYSTEM,
PC_ENGINE, MSX -> the libretro system; PC_TRACKER/MUSIC/CONSOLE -> no own system. SUPERSEDED (Johan 2026-11-15):
there is no cross-platform fallback. The earlier fixed order (Amiga, C64, ST, ...) is dropped; see section 2a.
Turrican 2 on Atari 8-bit -> no 8-bit entry -> Atarimania ST Turrican II (same ATARI family) -> else no game image.

## 3. Where it plugs in

- New `game_step(lib, key, st)` in `art_scrape.c`, called right before each `dz_step` call (lines ~453, ~527), same
  shape as `dz_step`: per-song id `sel_art_dz_id(key)`, `SEL_ART_SONG_META` for title (extend that op to return
  `album` too, one SQL column), skip when the song already has a `cover`.
- Order game > Demozoo > artist picture falls out for free: `dz_step` returns early when `cover` exists
  (art_scrape.c:335). Artist picture stays last (I1267 third part, not this design).
- Storage: same artwork kinds as Demozoo stills: `cover` = box scan (or first screenshot), `dz1`..`dz7` = the next
  screenshots. Why: `art_kinds` (art.c:231, I1384b) is the single place that decides slide-show frames and only
  accepts `cover`, `dz[1-7]`, `dz_video`; desktop `art_frames`/`art_big_frame` (plugins/ui/desktop/art.h:39) and MUI
  already draw them. New kinds would mean touching all three for no gain. Extra text kinds (not frames):
  `game_src` (provenance, e.g. `libretro:Commodore - Amiga/Turrican II - The Final Fight`), `game_info` (facts JSON,
  section 6), `game_miss` (epoch seconds, retried after `SEL_ART_SCRAPE_RETRY_DAYS`, same as `dz_miss`).
- Miss cache: `game_miss` per song id, as `dz_miss`. A network failure records nothing (existing rule).
- Privacy: request carries only game name and platform id; no song key, path, user or library id. Same base-URL knob
  pattern (`SELECTA_ART_GAME_URL`, default hippoplayer.se).
- Pref: reuse `art.demozoo` (prefs.def:83) as "online images for songs without an album"; `SELECTA_ART_SCRAPE=off`
  still kills all. Label text changes, key stays (decision D4).

## 2a. HARD rule: an image is only shown for the song's own platform (Johan 2026-11-15)

Johan: "it would be nice if turrican ii for c64 showed the c64 screenshot and not some other random platform".

Root cause today: non-Modland songs go through the Demozoo lookup by title + author (`art_scrape.c` `sel_dz_query`
~309, `dz_step` ~320). The server answer (`~/Code/hippoplayer.se/thoughts/shared/api/demozoo-lookup-v1.md`) has no
platform field and takes the first music entry in dump order; the client then takes the first production (earliest
release). Neither side filters by platform, so a C64 SID can get an Amiga or PC production's screenshot.

Rule, for every image source (Demozoo, Atarimania, libretro, HOL, Lemon64, web image search):
1. The song's platform family (`sel_platform_of_ext`, `src/platform/platform.c:128`) goes into the query, or the
   answer is filtered by it. Family -> source platform ids is one table on the server (single source of truth).
2. An image from another platform is never shown. A miss on the song's platform tries the NEXT SOURCE in the chain
   for that platform (C64: Demozoo C64 production -> Lemon64 -> libretro "Commodore - 64"), never another platform.
3. Inside one Selecta family, sibling systems count as the same platform: ATARI = 8-bit + ST (+ 5200/7800 only if
   the song is from those). This is what lets `Turrican 2 - Freedom.sap` show the ST Turrican II box. (Decision D3.)
4. Families with no machine (MUSIC, PC_TRACKER, CONSOLE) send no platform and only take album-art sources, never game
   images (a PC tracker module named "Turrican" must not get a game box).

Concrete change (build row 0, first):
- Server: each production in the Demozoo lookup answer gains `platforms: [<demozoo platform id>, ...]` (from the
  dump's production->platforms). New optional query param `platform=<selecta family id>`; when given, the server maps
  it to Demozoo platform ids, drops productions without a match, and picks the music entry whose production matches.
  Bump the API doc (`demozoo-lookup-v1.md`, additive field, old clients unaffected).
- Client: `sel_dz_query` appends `&platform=<family>`; `dz_step` skips productions whose `platforms` do not contain
  the family's ids (also guards an old server that ignores the param). No match = `dz_miss` for that platform, then
  the next source.
- Existing cached wrong-platform images: bump the dz cache version so songs re-resolve once (store kind `dz_src`
  already records the production; delete rows whose production platform does not match).

## 2c. Web image search as last fallback (Johan asked to evaluate, not decided)

Everything below is from knowledge, NOT verified this session (the research budget ran out); verify before a row.
- Google Custom Search JSON API (`searchType=image`): closed to new customers and being wound down; the
  "search the entire web" option ends around 2027. Was 100 free queries/day, then $5 per 1000. Not a base to build on.
- Bing Image Search API: Bing Search APIs retired August 2025. Dead.
- Brave Search API: has an image endpoint; free tier plus paid plans. The only live option of the three.
- DuckDuckGo: no official image API; scraping its endpoints is fragile and against its terms. No.
- Key handling: a key cannot ship in an open-source app. Options: hippoplayer.se proxy holds the key (cost and
  abuse are ours; same limiter as Demozoo), or a user-supplied key pref (no cost to us, almost nobody sets it).
- Query rule: `"<game> <platform name> box art"` for game songs, `"<artist> <title> cover"` for music. Confidence
  check: result title/URL must contain the normalised game name AND the platform name (rule 2a), else discard. Miss
  cached 30 days like `dz_miss`.
- Privacy: the query reveals the song/game title and platform to the search provider (through our proxy: provider
  sees our server, not the user). Must be a separate opt-in pref, default off.
- Rights: web search returns arbitrary copyrighted images with no licence; the curated sources above are cleaner.
- Verdict (recommended): skip for now. With Atarimania + libretro + platform-filtered Demozoo most game songs are
  covered; web search adds wrong-image risk that breaks rule 2a. Revisit with Brave through the proxy, opt-in, if
  the gap list stays large after rows 0-2.

## 3a. Server image cache on hippoplayer.se (Johan asked to evaluate, not decided)

Johan: "it would also be nice if we stored all images on our server and loaded them from there the second time it's
loaded so we only need to fetch them once from the other sites".

Two different things:
- Match cache (store the lookup RESULT: game id, source page URL, image URLs, facts). No image bytes. Every source
  allows this in practice; it is what the Demozoo lookup already does. Saves all repeat lookups, the client still
  fetches images from the source.
- Image cache (store the image BYTES and serve them from hippoplayer.se). That is redistribution of the source's
  images by us, not a per-user fetch, so it needs the source's terms or permission.

Per source (terms quoted where read this session; the rest is UNVERIFIED and must be read before a row):

| Source | Terms on storing and re-serving | Image cache allowed? |
|---|---|---|
| Hall of Light | footer "Content (c) 1998-2026 HOL TEAM"; no use or API page | No, needs permission (fold into the D1 mail) |
| Lemon64 | terms not readable (Cloudflare wall) | No, needs permission |
| Atarimania | pages "(c) Atarimania 2003-2026"; /about has no image terms | No, needs permission (heads-up mail can ask) |
| libretro-thumbnails | repo has no licence file; art belongs to the games' publishers | Mirror is how libretro itself distributes them; low risk, but not a granted licence (unverified) |
| Demozoo screenshots | Demozoo data is open, screenshots are uploads of the productions (unverified) | Probably yes with credit; read Demozoo's terms first |
| MusicBrainz / Cover Art Archive | MusicBrainz core data is CC0; CAA images keep their owners' copyright (unverified) | Match cache yes; image bytes like any cover art (low risk, credit) |
| ScreenScraper | API only for fully free apps, per-user quotas | No (re-serving defeats their quota) |
| Web image search results | arbitrary third-party images, no licence | No, never cache bytes |

Fallback where bytes may not be cached: server keeps the match result only (`game_src` + image URLs, 30-day refresh,
same as `dz_miss`); the client downloads the image itself from the source and caches it locally as it does today.
The source still sees one request per user per image, but no searches or page fetches.

Size: originals are 200-600 KB (HOL box 608 KB, Atarimania box 296 KB, libretro PNG ~200 KB). Re-encode to max
640 px JPEG ~60-100 KB. Per game: box + up to 7 screens ~400-600 KB. Only games actually requested get cached:
10k games ~5 GB, 50k ~25 GB (estimate, not measured).
Cap and eviction: hard cap 10 GB (server pref), LRU by last-served time; evict down to 90 % when over; never cache a
miss as bytes; re-check source every 180 days by HEAD/ETag. Store under `<source>/<platform>/<game id>/<frame>.jpg`.

Verdict (recommended): build the match cache now (free, all sources). Cache image bytes only for libretro and
Demozoo (after reading Demozoo's terms) at first; HOL, Lemon64 and Atarimania only if their owners say yes in the
same permission mail as D1. Web search: never.
