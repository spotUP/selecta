## I949b rig check

Question: on MUI 3.8, can the Selecta window be opened again (MUIA_Window_Open FALSE then TRUE, or TRUE again after a refused open) after the group content changed through MUIM_Group_InitChange / ExitChange and MUIA_ShowMe, so a refused first open (window too big for the screen) can retry with a compact layout?

Verdict: YES, reopen works. The layout does NOT have to be final before the first open.

Method: standalone MUI 3.8 probe (throwaway, not committed), built with the repo's Amiga toolchain (m68k-amigaos-gcc -m68020 -mcrt=nix20), run on vtcon rig 2 (silent) on its own 640x256 PAL hires custom screen (OpenScreenTags, MUIA_Window_Screen). One Group holding 40 Text buttons; ShowMe toggled for all of them inside InitChange/ExitChange on the group; window opened with `set(win, MUIA_Window_Open, TRUE)` and read back with GetAttr.

Rig log (T:reopen.log):

    screen 640x256
    A first open, 40 buttons: open=0 minh=441        refused, minimum 441 > 256
    B: showing 5
    B retry after refusal, 5 shown: open=1 minh=56   opens on the SAME window object after the refusal
    B2: close open=0
    C: showing 40
    C open grown again: open=0 minh=441              close, grow, reopen: refused again, no crash
    C: showing 5
    C open shrunk again: open=1 minh=56              shrink, reopen: opens

Also seen: _minheight(root) is valid after a refused open (the AskMinMax values stay in the object), which is what mui_open already logs. A first control run with 14 buttons (minimum 213, fits) opened at once and reopened normally, so open/close/ShowMe cycles are safe in general.

Limits: probe used one Group of Text objects, not Selecta's custom classes (canvas, aa* classes) or the real Application; those were not exercised. The probe does not tell whether Selecta's custom classes keep valid state across a close/open cycle (not needed for the refused-first-open case: a refused open never ran Setup/Show on the children beyond AskMinMax, as in the log).

Implication for I949b: both approaches are available. Cheapest and safest: keep mui_layout_for_screen before the first open (it already picks by screen size), and add a retry in mui_open: if open==0, take the next more compact layout step (mui_layout_map with a smaller tier or a compact flag), mui_apply_layout, and `set(s->win, MUIA_Window_Open, TRUE)` again on the same window object, no dispose and recreate. Stop and report MUI_FAIL_NO_WINDOW only after the most compact layout is refused. Rig measurement of a refused open stays in the existing "window minimum WxH" log line, so each retry step can log its own.
