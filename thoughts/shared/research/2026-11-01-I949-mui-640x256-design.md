# I949: the MUI UI must open on 640x256 (tall pixels)

Johan, verbatim: "the mui ui needs to scale down to 640x256"; "keep in mind that 640x256 use tall pixels and the ui needs to adapt".
Screen text seen: "Selecta: the MUI window could not open. Using the text UI. (the layout needs 670x619 px, more than the screen shows)".

Constraints: MUI 3.8 only. Mac desktop layout is the look reference. Full screen is the Amiga default, compact modes switchable (D-M4-3). Hires non-laced PAL pixels are about 2x taller than wide.

Evidence: rig report thoughts/shared/research/2026-11-01-I918-rig-report-2.md (I949 size breakdown) plus source reading. Nothing here was run on a rig; numbers marked "inference" are not measured.

## 1. What drives 670x619 and 530x459

Measured on rig 2 (Workbench window, 640x256 screen): root min 530x459.
- Main row (HGroup SIDEBAR / MAIN / DETAIL, mui_ui.c ~3030-3045): 526x384.
  - Sidebar 194x384. This is the height driver. mui_sidebar_group (mui_ui.c:930-975) builds: brand row, MUI_SIDEBAR_DOORS=8 door buttons (mui_map.h:582), a title/Create/Expand row, then side_dyn (mui_sidebar_dyn, mui_ui.c:871-907): a chips row plus up to MUI_SIDEBAR_ROWS=16 (mui_map.h:583) library rows as static AAText objects stacked vertically (side_dyn alone 132x192).
  - Main column 324x107 (list page with tool group, mui_main_group / mui_tool_group mui_ui.c:1171; pages mui_main_pages 1630-1676).
  - Detail 180x282 (mui_detail_group 1516-1594, art 64x64) is hidden at this width but still built.
- Player 440x72 (mui_player_group mui_ui.c:1001-1084). Height comes from the right column: volume row, extras row (mui_p8_extras_row 942-955), format/status row. Left column art is MUI_PLAYER_ART_PX=56 (mui_map.h:111).
- Width 526 = sidebar 194 + spacing 4 + main 324.

Laced own screen 640x512: "window minimum 670x619, screen 640x512, open 0". Cause (inference, consistent with the numbers, breakdown not measured): mui_aa_font_px (map/mui_aa.c:168-171) returns topaz 8 at <=256 rows and a 13 px font at <=600 rows. mui_aa_metrics (mui_aa.c:177-188) then grows every control: pad 6/3 to 10/6, icon 12 to 18, control height 14 to 30. The font is chosen per screen rows (mui_aa_draw.c:164). So lacing doubles the rows and the controls grow with them; the laced screen never helps.

Why the sidebar is there at 640: sel_uim_breakpoint_for_tier (src/uimodel/layout.c:27-31, I526) returns SEL_UIM_BP_ICON_SIDEBAR for 600-699 px on the bitmap tier. uimodel asks for a labelled rail of SIDEBAR_RAIL_LABELLED=160 px (layout.c:17, 150-153). MUI ignores the rail form and builds the full sidebar with the stacked library rows.

## 2. Why mui_layout_min_height is wrong, and the right source of truth

mui_layout_min_height (map/mui_screen.c:22-29) sums a "mini layout, sidebar and detail hidden" from topaz-8 constants (map/mui_map.h:389: MUI_FONT_H 8, MUI_STRING_H 14, MUI_TEXT_FRAMED_H 12, MUI_SLIDER_H 12, MUI_GROUP_SPACING 4, MUI_WIN_CHROME_H 24, MUI_LIST_MIN_ROWS 2) plus mui_button_height (mui_screen.c:14). It predicted 304, MUI asked for 459. It is wrong for two reasons:
1. It models a layout that is not the one built: the sidebar is shown (section 1) and the model assumes it is hidden.
2. It is a second source of truth. The constants do not follow the tier fonts and metrics (mui_aa_metrics), nor any later class change. It will drift again.

mui_screen_plan (mui_screen.c:30-48) laces when the Workbench height is below that guess. With root cause 2 in section 1, lacing makes the window bigger, not smaller.

Right source of truth: MUI itself. MUIM_AskMinMax runs during the window open. After a refused open, _minwidth/_minheight of the root hold the real minimum (mui_ui.c:3064-3090 already logs them and builds the "why" text). The open attempt is the measurement.

Design:
- Delete mui_layout_min_height, the MUI_*_H constant model and the lacing branch of mui_screen_plan.
- Add a pure map function, e.g. `mui_open_ladder(step, screen_w, screen_h, min_w, min_h)`, that returns the next action after a refused open: apply the next more compact layout class and retry, or give up (text UI with the existing "why" text). Steps: full layout, compact layout (section 3), then text UI. No lace step.
- mui_ui.c window open (around 3064) loops on the ladder: set the layout class (ShowMe/weights through mui_apply_layout 2928-2943), set MUIA_Window_Open again, read the min size if refused.
- Risk to check on the rig first (I949c): MUI 3.8 must accept a second MUIA_Window_Open after ShowMe changes on a closed window. If it does not, fall back to choosing the class before the first open from the screen size (mui_layout_for_screen 2945-2957) and keep the open attempt only as the check.

## 3. Layouts at 640x256 and 640x512 laced

Budget, Workbench window on 640x256: Workbench title ~11, window title ~11, bottom border ~10, side borders ~4 each. Inner about 616x224. Own screen (borderless, full screen default): 640x256 minus the screen title if shown, about 640x244.
Target root minimum for the compact class: at most 600x220 (fits both).

Compact class (bitmap tier, width 600-699, height <= 300 rows):
- Sidebar becomes the labelled door rail uimodel already asks for: 160 px wide, 8 doors (icon + label), spacing 1. Brand row hidden. The Your Library block (title row, chips, 16 static rows) is not shown in the rail; it is the Library main page (the Library door already opens it, I673 behaviour on the Mac labelled sidebar). Rail height: 8 doors x ~16 = ~128 px.
- Main column: at least 240 px wide (MAIN_MIN_W), takes the rest (~436). List page min 2 rows (AAList min already 2*pad_y + title + one row, mui_aalist_class.c:132). Viz and Pattern pages are already pages in main, no change.
- Detail column hidden (already). Now Playing reachable as a main page (the detail content moves into a main page in this class; desktop UI has the same fold at narrow widths).
- Player: one band, target <= 36 px. Left: art 56x28 (tall-pixel square, section 4) + title/artist. Centre: transport row and seek row. Right: volume and format/status on one row. Extras (album, speed) move to the menu.
- Height: main row ~170 (rail 128, main list fits) + spacing 4 + player 36 = ~210. Width: 160 + 4 + 436 = 600.

640x512 laced: drop the laced plan (section 2). If a laced screen stays offered (decision for Johan, below), it uses the topaz-8 metrics of the 256-row tier so the layout is the normal full class with room; the font choice follows the pixel aspect and line density, not raw row count.

Full class (RTG, 800x600 and up): unchanged.

## 4. Tall pixels: one place reads the aspect

Read once, at screen choice in mui_screen_open (mui_ui.c:537-600), which already calls GetDisplayInfoData(DTAG_DISP) at mui_ui.c:556. DisplayInfo.Resolution (Point, ticks per pixel) gives the aspect: hires PAL non-laced about 22x44, aspect 2; laced and RTG about 1. Workbench window case: same call on the Workbench screen's display ID (GetVPModeID), or GetScreenDrawInfo dri_Resolution.

- Pure map function `mui_pixel_aspect_q8(res_x, res_y)` returns aspect x 256 (512 for hires PAL, 256 for square), clamped to 1..2.
- Stored once in mui_aa_metrics_t as `aspect_q8`, with derived vertical sizes: icon_h, check_h, pad_y, art height. mui_aa_metrics (mui_aa.c:177-188) takes the aspect as an argument.
- Consumers (all read the metrics, none reads DisplayInfo):
  - AAButton size and icon draw (aabtn_measure mui_aabtn_class.c:93-100, draw 205-209): icon icon_px x icon_h. At aspect 2 a 16x8 icon; needs a new atlas size in mui_icon_sizes (map/mui_icons.c, header mui_icons.h:35), drawn from the existing artwork.
  - AACheck: check_px x check_h (mui_aabtn_class.c:100).
  - Art panels: player 56 and detail 64 wide, height = width / aspect.
  - Vizarea minimum (mui_vizarea_class.c:80-90).
  - Viz glyph scale (plugins/shared/viz/glyphs.h:50-52, vs_text square scale): separate x and y scale, so PatternScope/sidregs labels are not 18 px tall (I950 is the same cause).
  - mui_button_height and group spacing (vertical spacing halves at aspect 2).
- Text (topaz 8) needs no change; the font already matches the pixel shape.

## Decisions for Johan (product behaviour)

## 6. Now Playing as a compact main page (I960)

Goal: in the compact class (640x256, section 3) the detail column is hidden (I949d) and the player band keeps only title, artist and Like. I960 makes the full Now Playing content reachable as a page of the main slot, laid out after the Mac Now Playing page (plugins/ui/desktop/desktop_ui.c draw_nowplaypage, 12442), packed to the compact tier (Johan answer 4: Mac order and grouping, not Mac spacing).

### 6.1 What exists (searched before designing)

Searched: `detail`, `np_`, `NOWPLAYING`, `MUI_PANE_`, `mui_pane_`, `CTL_DOOR_BASE`, `mui_screen_compact`, `nowplaying` in plugins/ui/mui, src/uimodel and plugins/ui/desktop.
- `mui_detail_group(s)` (mui_ui.c:1690) builds the whole Now Playing content: art panel, np_title/np_artist/np_album/np_note AATexts, Like (I1125), viz area + picker, and the Lyrics/Info/Tracks AATabs page group (lyrics AAList, "Next in Queue" + np_up[3], info_list, trk_group). `mui_detail_refresh` (1880) fills every one of them from the engine state by signature. Reused whole; no second set of objects.
- The main slot is already a MUI 3.8 page group: `mui_main_pages` (1813) with panes MUI_PANE_LIST, MUI_PANE_VIZ, MUI_PANE_TRACKER (map/mui_map.h:352, table `k_panes` map/mui_views.c:310). `mui_pane_show` (1855) switches by `MUIA_Group_ActivePage` only. The View menu builds one item per pane from `mui_pane_title`/`mui_pane_shortcut` (mui_ui.c:421-424, handler CTL_PANE_BASE at 2982).
- Doors: the uimodel door table has "Now Playing" and "Song Information" with a NULL engine line (src/uimodel/doors.c:12-13); the MUI door handler (mui_ui.c:3045-3051) does nothing for them ("an in-window page"), so in the compact class the Now Playing door is dead today. The I949c compact rail builds every door, so the door is on screen at 640x256.
- `mui_screen_compact()` (mui_ui.c:949) decides the class before the window tree is built; I949c (rail) and I949d (band) already branch on it at build time.
- Mac: the Now Playing page is reached by the door only (`np_page = pg == SEL_UIM_PG_NOWPLAYING`, desktop_ui.c:10616); the default key table (src/uimodel/keybind.c:153) has no Now Playing key; the player bar has no click to it. Mac page order: heading "Now Playing", cover square left, title / artist / format to its right, then "Next in Queue" with up to 8 entries. Sentinel `np_page_draws`.

### 6.2 How the page is reached

- Primary: the "Now Playing" door in the compact rail opens pane MUI_PANE_NOWPLAYING (as the Mac door does).
- The "Song Information" door in the compact class opens the same pane with the Info tab active (the detail Info tab is the MUI Song Information content; no second info list).
- View menu: "Now Playing Page" item from the k_panes entry, no shortcut (the Mac has no key; `n` is NEXT). Shown only in the compact class.
- Leaving: any door with an engine line already calls `mui_pane_show(s, SEL_UIM_PG_HOME)`; the v/t keys and the View menu switch to the other panes. No new back control.
- Full class: unchanged. The door map returns "no pane" there; the detail column shows the content as today.
- Player band click (title/art): decision for Johan below, not in the rows.

### 6.3 Which objects are reused, and how they move

- `mui_detail_group` gains one argument: `mui_detail_group(s, compact)`. Every child is built by the same code; `compact` only changes the arrangement:
  - full (unchanged): the vertical stack of today.
  - compact: a page heading AAText "Now Playing" (MUI_LBL_SECTION), then one HGroup row [art panel | VGroup(np_title, np_artist, np_album, np_note) | Like], then the AATabs strip and the Lyrics/Info/Tracks page group filling the rest. The viz area and its picker are not built in compact (the Visualizer page is its own pane, key v; the Mac page has no viz either), so `s->viz_area`/`s->cyc_viz` stay NULL there; I960c greps every user of `viz_area` and `cyc_viz` and confirms each NULL-checks.
- The window build calls `mui_detail_group` once, before the tree, into a local, and hands it either to the detail slot (full) or to `mui_main_pages(s, np)` as page MUI_PANE_NOWPLAYING (compact); the detail slot then gets an empty Rectangle (it is hidden in the compact class anyway). The local is required: `mui_main_pages` and `mui_detail_group` are arguments of the same window tag-list call today, and C leaves their evaluation order unspecified.
- `mui_main_pages` always adds a 4th page so pane indices are fixed: the np group in compact, an empty Rectangle in full.
- Art: the compact page art takes its width from `mui_np_page_plan` (6.6) and its height from `mui_art_height(w, aspect)` (tall-pixel square, section 4), not MUI_DETAIL_ART_PX.

### 6.4 What is shown, in which order, at 640x256

Main column about 436 x 170 (section 3). Topaz 8, compact metrics tier (I949e), aspect 2:
1. Heading "Now Playing" (one text row, about 10).
2. Top row (about 34): art 64 wide x 32 tall (square on tall pixels); right of it title, artist, album and the missing sample bank note, one row each; Like at the right end, same control id as before (CTL_P4_BASE + P4_LIKE).
3. Tabs strip "Lyrics", "Info", "Tracks" (about 12).
4. The active tab page takes the rest (about 105): Lyrics = lyrics list (3 rows) + "Next in Queue" + 3 entries; Info = info_list (6 rows, scrolls); Tracks = pattern rows (trk_group, shown only with pattern data).
Texts are single-line AATexts that clip at the page width; nothing wraps.

### 6.5 Page switch without a full-window relayout (I966 flicker)

- The switch is `set(main_pages, MUIA_Group_ActivePage, pane)` only, the path the Visualizer and Pattern panes use. A page group's minimum and maximum are computed over all pages at window layout time, so a page switch redraws the main slot only: no `MUIM_Group_InitChange/ExitChange`, no ShowMe, no OM_ADDMEMBER at switch time. All objects are built once at window build.
- Risk: the 4th page raises the main slot minimum to the tallest page. The np page minimum must stay at or under the main height budget (about 170 rows at 640x256), else the root minimum passes 600x220 and the ladder (section 2) falls to the text UI. The pure plan carries that budget and its host test asserts it; the rig reads the window minimum log line.
- `mui_detail_refresh` keeps filling the texts while the page is not active. I960b checks that `mui_aatext_set` and `set(..., AAL_Count)` do not draw into a page that is not shown; if one does, the fix goes in that class's draw gate, not in the caller.

### 6.6 Pure host-testable functions

All in plugins/ui/mui/map, declared in mui_map.h, tested in tests/ui/mui_contract_test.c (existing mui-contract target; no CMakeLists change).
- `MUI_PANE_NOWPLAYING` added to the pane enum before MUI_PANE_COUNT; `k_panes` entry `{SEL_UIM_PG_NOWPLAYING, NULL, "Now Playing Page"}`. `mui_pane_of_action` and `mui_pane_shortcut` get a NULL-action guard (today they would pass NULL to strcmp and txt_bindings_key_for). `mui_pane_of_page(SEL_UIM_PG_NOWPLAYING)` returns MUI_PANE_NOWPLAYING; `mui_pane_shortcut` returns '\0' for it.
- `uint32_t mui_door_pane(uint32_t door, uint32_t compact, uint32_t* tab)` (map/mui_views.c): for a door with a NULL engine line, in compact, returns the pane to show and the tab (0 Lyrics, 1 Info); returns MUI_PANE_COUNT in full and for every door with a line. Reads the door's page through `sel_uim_door_at` + `sel_uim_page_by_name`, no index constants.
- `void mui_np_page_plan(const mui_aa_metrics_t* m, uint32_t main_w, mui_np_page_plan_t* out)` (map/mui_layout.c): art_w, art_h (via aspect_q8), text rows, lyric rows, next-in-queue rows, info rows, min_h. The builder reads art size and row counts from it, so the plan moves the output. Host cases: compact tier at aspect 512 gives min_h <= 170 and art 64x32; aspect 256 (user-chosen laced, Johan answer 1) gives art 64x64 and still fits the 256-row tier main height.
- Source checks (strstr on MUI_UI_SOURCE, the test_screen_plan pattern): the door handler calls `mui_door_pane`; `mui_main_pages(s, ` takes the np group; `mui_detail_group(s, ` appears once as a call.
